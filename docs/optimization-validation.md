# 逻辑与性能优化验证（2026-09-06）

## 本次行为调整

- 发件邮箱 ID 使用独立递增序列；迁移会预留历史记录和计划中引用的旧 ID。删除账号后，原计划仍保留原选择，不会因清空选择而自动使用全部邮箱。
- 已完成任务再次发送会创建独立发送轮次；中途停止/重启继续时，只使用本轮记录去重。原历史记录保留。手动补发计入当前轮次，空闲任务的进度会同步更新。
- 运行、启动或暂停中的计划通过后端注册表锁定稿件、邮箱和间隔编辑；先停止并等 worker 退出再修改。参与活动任务的账号也受到修改/删除保护。
- 手动 IMAP 检查移到后台阻塞线程；自动与手动检查共享互斥门。DNS/TCP 连接限时 15 秒，TLS/收发读写限时 30 秒；每次最多读取 200 封、每批 10 封。
- 邮箱身份变化时重置游标并递增命名空间；UIDVALIDITY 改变时回扫。回复去重包含邮箱命名空间，历史回复保留。
- 新同步回复保存服务器真实收件时间，统一到本地时区；同步时间单独保留。已有旧记录没有可靠原始时间时保持原值，不猜测补写。
- 回复搜索和分页由后端完成，返回真实总数，不再只搜索最新 300 条。单个计划的投递详情覆盖该计划完整历史。

## 第四轮：发送前校验与手动发送互斥（2026-09-06）

### 修复与优化

- 自动任务先在事务中完整读取任务、设置、稿件、附件及本轮投递历史，并成功写入初始进度后才进入发送。缺失稿件、损坏设置、历史查询错误或进度写入错误会停止任务，不当作空数据继续发送。
- 收件人、任务/稿件账号选择、稿件关联和邮件模板 JSON 使用严格类型解析，避免损坏的账号列表被解释为“使用全部邮箱”。
- 附件读取区分“确实没有附件”和“名称/内容缺失、类型损坏或稿件已删除”。自动、手动、重发及测试邮件读取附件的错误都会向上传递，不再静默丢附件发送。
- 邮件发出后如投递记账失败，自动任务停止剩余队列并提示先核对发件记录；失败的数据库事务回滚任务计数、账号最近发送时间和投递记录。
- 手动发送和历史重发使用后端按稿件互斥的生命周期预留，覆盖网络等待到记录写入。预留同时保存原账号和关联任务，防止等待中编辑/删除关联配置、重置轮次，或与自动任务同时启动。提前返回、异步任务取消会释放预留，网络等待期间不持有数据库互斥锁。
- 定时任务遇到关联手动发送时保留 scheduled，下一次调度再尝试。历史记录关联的任务即使已经更换稿件，也按任务 ID 保护。
- 删除稿件会触发全局孤儿任务清理，因此手动发送期间暂缓稿件删除，待记录保存后再操作。账号禁用仍不撤销已进入 SMTP 调用的单封邮件。
- 活动任务的历史重发按钮同步禁用；详情内手动发送期间禁止继续重发、添加和移除编辑。

## 第五轮：稿件互斥、待确认投递、收件预算与详情分页（2026-09-06）

### 四项修复

1. **不同自动任务共享稿件**
   - 在任务注册表锁内原子申领稿件集合，不再仅检查任务 ID；暂停保留占用，多稿件申领冲突时不留下部分占用。
   - 立即启动和定时调度均执行检查；定时任务遇到占用保留原定时状态，后续调度再尝试。原有手动/自动互斥继续生效。

2. **SMTP 成功与本地记账之间的空隙**
   - 新增 `outgoing_attempts`。自动、手动和历史重发在网络操作之前持久化任务/轮次、账号、稿件、收件人、主题、Message-ID 和待确认状态；主数据库使用 WAL + `synchronous=FULL`。
   - 正常投递成功时，投递历史、进度、账号时间和尝试状态在同一事务提交，按 Message-ID 幂等记账。保存失败、进程退出或发送结果不明时保留待确认记录，阻止直接继续、重置和其他发送路径绕过；相关稿件/任务/账号的破坏性修改也被拦截。
   - 明确的 SMTP 负响应及构建错误仍按既有规则处理；无明确服务器拒绝的连接错误保守视为结果不明，停止自动重试。这可能要求用户核对实际上尚未发出的连接失败，避免将已接收但回执丢失的邮件自动再发。
   - 计划“记录”增加发件账号、收件人、主题、尝试时间及 Message-ID，提供“已发出，补记成功”和“未发出，解除待确认”。两种确认本身都不发邮件，并写入核对日志。仅发件箱中没有记录不足以证明邮件未发出。
   - 补记成功使用原发送尝试时间作为本地历史时间，不把今天的确认时间冒充原发送时间；该时间是近似值，不代表服务器精确接收时刻。普通成功仍记录实际记账时间。
   - 循环任务恢复时去重当前循环已提交的投递，开始有意的下一轮时分配新轮次 ID，不清掉累计进度。循环下一轮的重复投递仍是既定功能。
   - 此机制降低自动重复发送风险，不声称跨 SMTP/SQLite 实现分布式 exactly-once。错误的人工确认仍可能导致重复或漏投。

3. **收件大小与整轮耗时**
   - 先查询 `RFC822.SIZE`，单封超过 **2 MiB** 时不下载完整 MIME，记录 UID 提示后继续其他邮件；原邮件留在服务器，需在邮箱客户端查看。
   - 每账号每次最多处理 200 封、累计完整 MIME 最多 **8 MiB**；底层网络读取预算 **32 MiB**。正常正文读取仍使用 `BODY.PEEK[]`，不标记为已读。
   - 每次底层读写根据剩余绝对时间设置超时，覆盖 TLS 握手、IMAP 命令及持续慢速传输：单账号最多 **60 秒**，整轮网络扫描预算 **120 秒**。
   - 达到预算或中途失败时保存已完成前缀，不推进失败邮件 UID，下一次接着处理；扫描起始账号轮换，避免后面的账号一直排在慢账号之后。

4. **投递详情的完整历史加载**
   - 详情改用后台线程中的 SQLite 按收件人聚合分页；返回当前页次数、最近投递 ID/时间和全量总数，而非全部历史记录。
   - 状态筛选先于分页，搜索覆盖所有收件人，保留名单顺序和重发所需的最新记录 ID；页长后端上限 100，界面提供 10/20/50。
   - 索引兼容旧记录中的显示名、大小写和空格；Message-ID 查询也建立索引，避免新幂等检查每封扫描全部历史。
   - 查询失败隐藏旧数据并禁用发送操作，支持重试；忽略过期请求，搜索和筛选回到第一页。任务事件不再拉取全部投递历史。
   - 旧 `list_deliveries` 接口保留兼容，详情界面已不再调用它。
